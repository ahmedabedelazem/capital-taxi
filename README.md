# تاكسي العاصمة | CAPITAL TAXI

منصة نقل عربية مخصصة للعريش وشمال سيناء، بثلاث بوابات مترابطة: العميل والسائق والإدارة.

## التقنية

- Next.js App Router + TypeScript
- Tailwind CSS وواجهة عربية RTL متجاوبة
- Firebase Authentication للمتصفح وFirebase Admin للخادم
- Firestore كقاعدة بيانات لخدمات الخادم
- هوية Premium Dark Luxury

## التشغيل المحلي

```bash
npm install
cp .env.example .env.local
npm run dev
```

ثم افتح http://localhost:3000.

## بوابات التطبيق

- `/` الصفحة الرئيسية
- `/login` تسجيل الدخول وإنشاء الحساب بالبريد أو Google
- `/customer` بوابة العميل: طلب رحلة، اختيار المركبة وطريقة الدفع، تحديد المواقع، متابعة حالة الرحلة، سجل الرحلات، والدعم.
- `/driver` بوابة السائق: طلب الانضمام، التوفر، الموقع، عروض الرحلات، الرحلة النشطة، سجل الرحلات، والدعم.
- `/admin` بوابة الإدارة: مؤشرات التشغيل، اعتماد السائقين، متابعة الرحلات وتصفيتها، إعدادات التسعير والتوزيع، وإدارة الشكاوى والرد عليها.

## إعداد البيئة

املأ قيم Firebase Web SDK العامة في `.env.local`:

- `NEXT_PUBLIC_FIREBASE_API_KEY`
- `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`
- `NEXT_PUBLIC_FIREBASE_PROJECT_ID`
- `NEXT_PUBLIC_FIREBASE_APP_ID`
- `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`
- `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` لتفعيل Google Maps وPlaces

قيّد مفتاح Firebase API ومفتاح Google Maps في Google Cloud بنطاقات الموقع وواجهات API المطلوبة. القيم العامة ليست بديلاً عن قواعد Firebase الآمنة.

على الخادم فقط، أضف:

- `FIREBASE_PROJECT_ID`
- `FIREBASE_SERVICE_ACCOUNT_JSON` أو Application Default Credentials
- `DISPATCH_WORKER_SECRET` سراً عشوائياً لا يقل عن 32 حرفاً
- `APP_BASE_URL` عنوان HTTPS الأساسي للنشر، ليعيد مجدول التوزيع استدعاء العامل الداخلي

لا ترفع ملفات service account أو أسراراً أو ملفات `.env.local` إلى Git.

## المصادقة والصلاحيات

- `POST /api/auth/session`: يستبدل Firebase ID token بجلسة خادمية في Cookie من نوع HttpOnly.
- `DELETE /api/auth/session`: ينهي الجلسة.
- `GET /api/me`: يعيد هوية المستخدم والدور بعد التحقق الخادمي.
- أدوار الإدارة والسائق تعتمد على Firebase custom claims موقعة؛ لا تقبل الواجهة أو الخادم دوراً موثوقاً من جسم طلب العميل.
- اعتماد السائق يتطلب claim موقّعاً وسجل طلب اعتماد خادمي بحالة `approved`.

## الوظائف الموجودة حالياً في المستودع

### العميل

- إنشاء طلب رحلة والتحقق من البيانات وحساب تقدير السعر على الخادم.
- اختيار فئة المركبة وطريقة الدفع المتاحة في النموذج.
- استخدام Google Places لاختيار العناوين وإحداثياتها، مع طلب إذن الموقع عند استخدام GPS.
- متابعة حالة الرحلة وبيانات السائق بعد إسناد الرحلة.
- عرض خريطة Google Maps بعلامات الانطلاق والوجهة وموقع السائق عند توافره.
- عرض سجل الرحلات وسجل تذاكر الدعم وردود الإدارة.

### السائق

- إرسال طلب الانضمام وانتظار اعتماد الإدارة.
- تشغيل/إيقاف التوفر، وإرسال الموقع بعد موافقة المتصفح.
- استلام عروض الرحلات وقبول العرض من خلال عملية ذرية على الخادم.
- متابعة الرحلة النشطة وتحديث حالتها.
- عرض سجل الرحلات وسجل تذاكر الدعم وردود الإدارة.

### الإدارة

- عرض مؤشرات الطلبات المعلقة والرحلات النشطة مع توضيح أن القوائم محدودة وليست إحصاءً تاريخياً شاملاً.
- مراجعة طلبات السائقين واعتمادها أو رفضها.
- تصفية الرحلات حسب الحالة والبحث في بيانات الرحلة.
- ضبط التسعير ونطاق الخدمة ومراحل التوزيع.
- متابعة تذاكر الدعم، وتغيير حالتها، وحفظ رد الإدارة.

## إعدادات وبيانات Firestore

تعتمد واجهات الخادم على مجموعات/وثائق منها:

- `config/tripPricing`: التعريفة ونطاق الخدمة.
- `config/dispatch`: أنصاف أقطار مراحل التوزيع ومدة العرض وحد العروض.
- `driverApplications/{uid}`: طلبات السائقين ومراجعتها.
- `drivers/{uid}`: حالة التوفر وآخر موقع.
- `trips/{tripId}` و`tripOffers/{tripId}_{driverUid}`: الرحلات والعروض.
- `tripIdempotency/{hash}`: منع إنشاء رحلات مكررة.
- `supportTickets` و`supportRateLimits`: تذاكر الدعم وحدود الإرسال.
- `adminAuditLogs`: سجل إجراءات الإدارة.

هذه أسماء ومواصفات يعتمد عليها الكود؛ لا يعني وجودها في المستودع أن البيانات قد رُحّلت أو أن إعدادات Firebase التشغيلية قد نُشرت.

## حدود التشغيل الحالية

- خريطة العميل تعرض علامات المواقع وموقع السائق الذي يرجعه API؛ لا تدّعي رسم مسار ملاحي أو توفير توجيه turn-by-turn.
- ظهور الخريطة وميزة البحث بالعناوين يتطلبان ضبط `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` وتفعيل Maps JavaScript API وPlaces API.
- تحديث موقع السائق مشروط بإذن الموقع وحالة التوفر أو وجود رحلة نشطة. دقة وتواتر ظهور الموقع يعتمدان على تحديثات السائق واستجابة الشبكة.
- عامل `dispatch/sweep` موجود، لكنه لا يعمل تلقائياً حتى يتم إعداد Cloud Scheduler أو مجدول خارجي موثوق.
- أضيف ملف `firestore.indexes.json` وربطه في `firebase.json`؛ يلزم نشر الفهارس إلى مشروع Firebase المقصود قبل الاعتماد على الاستعلامات التي تتطلبها.
- نجاح CI يثبت نجاح lint وTypeScript وProduction build في بيئة GitHub Actions، ولا يثبت اتصال Firebase الفعلي أو نجاح الرحلات على بيئة تشغيل منشورة.
- لم يتم من خلال هذا التعديل نشر التطبيق أو إنشاء Cloud Scheduler أو نشر فهارس Firestore أو تغيير بيانات Firebase وقواعده.

## تشغيل مجدول توزيع الرحلات

العامل الداخلي لا يبدأ من تلقاء نفسه؛ يجب إعداد Cloud Scheduler بعد نشر التطبيق وضبط متغيرات الخادم. راجع [دليل مجدول التوزيع](docs/DISPATCH_SCHEDULER.md) قبل التفعيل، وتأكد من اختيار مشروع Google Cloud الصحيح.

## الأمان

- التحقق من الهوية والدور على الخادم.
- لا تفتح قواعد Firebase لتسهيل التطوير.
- لا تسمح للعميل بتعديل المحافظ أو العمولات أو أدوار الإدارة.
- لا تعرض بيانات تواصل العميل قبل إسناد الرحلة.
- لا تجمع موقع السائق إلا عندما يكون متصلاً أو لديه رحلة نشطة، وبموافقة المتصفح.
- احتفظ بأسرار الخادم وبيانات Service Account خارج المستودع.
